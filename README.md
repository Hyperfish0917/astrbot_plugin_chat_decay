# AstrBot 群聊唤醒与对话衰减

让机器人在 QQ 群里适度接话、逐轮衰减，并在不合适的时候停止。**v1.4.0 修复了旧版本 80% / 50% 未命中后持续重试的问题**，增加低成本的接话关联判断及回复后计数。

- 适配目标：AstrBot **v4.29.3 及以上**，主要面向 OneBot v11（如 SnowLuma）。
- GitHub：<https://github.com/Hyperfish0917/astrbot_plugin_chat_decay>
- 许可：[MIT](LICENSE)，作者：Hyperfish0917。

## 它如何决定是否接话？

**直接唤醒**：AstrBot 已识别的 @、引用机器人、唤醒前缀，以及插件关键词包含匹配、定向戳一戳，不经过随机抽签。即使在冷却中也允许主动唤醒。命中关键词不要求在句首。Slash 指令交给其他插件处理，不记录为新话题。

**普通消息**：

1. 没有活跃话题时，每条普通消息以默认 **20%** 概率尝试主动插话。冷启动未命中**不会**进入强制冷却。
2. 机器人**真正发送默认 LLM 回复后**，建立当前话题，并记录发言用户和时间。仅调用模型但没有结果，不推进轮数。
3. 30 秒内同一发言人发来带有接话语气的消息（例如“那第二部呢？”“所以呢？”“怎么会这样？”），才进入连续跟进概率：**第 1 轮 100%、第 2 轮 80%、第 3 轮 50%**。
4. 同一轮**只抽签一次**。有效跟进概率没命中，结束当前话题，默认进入 **90 秒**冷却；也可以配置为立即恢复 20% 冷启动。第三次跟进**实际回复发送后**进入冷却。
5. 与上次机器人回复间隔超过 30 秒、换了发言用户，或内容看不出接话迹象时，**不继承高跟进概率**，按普通消息的 20% 处理。

**重要限制**：这是一套“发言人 + 时间 + 语气词”的低成本启发式判断，**不理解聊天语义**，不能保证识别所有话题关联。引用、@ 与关键词属于显式强制唤醒，会绕过概率。请勿同时开启其他会对所有群消息独立调用 LLM 的插件，否则无法由本插件阻止那些独立回复。

## 安装和更新

1. 在 AstrBot WebUI「插件」中使用 GitHub 仓库地址安装或更新：`https://github.com/Hyperfish0917/astrbot_plugin_chat_decay`。
2. 更新后重新加载插件。现有配置会被保留；新加的配置项会按默认值补充。
3. 在插件配置页检查触发词和概率。插件详情页的「恢复默认设置」View 还可以分别恢复四项概率或**全部默认配置**。
4. 正式启用前建议先在测试 QQ 群验收，特别是不同群友交谈、引用回复和流式回复。

## 配置表

| 参数 | 默认 | 含义 |
|---|---:|---|
| `keywords` | 肥鱼、鲸鱼、deepseek | 包含任意一词直接唤醒；可自行修改 |
| `ignore_case` | true | 忽略英文大小写 |
| `base_passive_rate` | 0.20 | 冷启动主动插话概率 |
| `decay_rate_1` | 1.00 | 有效跟进的第 1 轮概率 |
| `decay_rate_2` | 0.80 | 有效跟进的第 2 轮概率 |
| `decay_rate_3` | 0.50 | 有效跟进的第 3 轮概率 |
| `max_turns` | 3 | 最大成功跟进次数 |
| `cooldown_seconds` | 90 | 跟进失败或满轮后的冷却秒数 |
| `session_timeout_seconds` | 30 | 机器人上次实际回复后的话题有效窗口 |
| `followup_require_cue` | true | 跟进需要同一人且含“那、所以、怎么、呢、？”等接话迹象；关闭则仅要求同一人 + 时间 |
| `miss_action` | cooldown | 有效跟进未命中后：`cooldown`=冷却，`baseline`=立即返回冷启动；**普通消息 20% 未命中不触发此规则** |

配置值在 WebUI 中调整，不需要手改 Python。所有状态只存内存，每个机器人、适配器、群组分开，不采集消息内容和统计数据，也不发送遥测。日志仅记录操作类型、轮次、概率与命中状态，不打印聊天原文。

## 典型例子

```text
群友 A：肥鱼，推荐一部电影。       → 关键词强制唤醒；机器人完成回复
群友 A：那第二部呢？            → 有效跟进第1轮，100% ，机器人完成回复
群友 A：所以你的意思呢？         → 有效跟进第2轮，80%：若未命中，立刻结束并冷却90秒
群友 A：那再说说？               → 冷却中，不会重复抽签
群友 A：@机器人 请继续           → 显式唤醒，始终允许
```

如果插入群友 B 的无关消息，它不会得到 A 话题的高概率接话权；但它仍可按 20% 进行普通冷启动抽签。

## 技术实现与限制

- AstrBot v4.29.3 以 `event.is_at_or_wake_command` 控制默认 LLM 链路。插件只在抽签命中或明确唤醒时设置此标记，**不会调用 `stop_event()` 阻断其他插件**。
- 非流式回复通过官方 `after_message_sent` 钩子并确认发送操作及 `LLM_RESULT` 后推进计数，不把模型错误回复计作正常轮次。
- v4.29.3 的流式回复没有统一的 `after_message_sent` 钩子，因此插件仅为本条已获准消息临时包装 `event.send_streaming` 实例方法，**在适配器处理完整个含可见消息段的发送操作、且记录了发送动作后**计数；这不是 QQ 服务端送达确认。流式异常或适配器特殊实现需在真实环境中确认。
- 等待回复期间阻止普通消息叠加触发模型；若连续 **90 秒**仍无可确认回复，会放弃该待处理状态，允许后续消息重新参与冷启动。显式唤醒仍可越过等待。
- 插件只控制本插件允许的**默认 LLM 唤醒路径**，不干预其他插件内部独立调用、平台系统消息、跨插件冲突或 QQ 服务端投递。

## 测试

```sh
python -m pip install pytest pytest-asyncio
python -m pytest -q
```

测试覆盖按轮概率、失败立即停止、成功发送再计数、并发等待、超时、冷启动、不同发言人及群组、重置、流式输出等。**这些是模拟框架的单元测试，不代表已在实际 QQ 群验证成功**。强烈建议先使用一个测试群，检查 AstrBot 是否使用了其他消息唤醒插件或配置。
